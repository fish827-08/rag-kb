# kb v2.4.3 发布说明（2026-11-03）

本版是一次**排查后的加固小版本**，不是“修复某个已证实 bug”的版本。

## 结论先行

起点是压测库重启后报 `Error loading hnsw index`。按 680 / 640 / 600 / 520 / 400 / 200 条逐级复现后，
最终在**非沙箱、同一条终端链路**下重新执行同一工作负载：680 条 × 5 次进程重启全部通过。
报错根因是外部环境清理 Chroma 的 `chroma.sqlite3-journal`（沙箱与普通终端交替访问同一数据目录），
不是 kb 的代码缺陷。

因此本版不做“修 bug”声明，只做两项低风险加固，并把这轮排查写进 README 排障。

## 改动

### 大库读取分页

- `ChromaStore.iter_all()` 从“一次无 limit 的全量 `get()`”改为**每批 500 条**分页拉取（`ITER_BATCH=500`）。
- 返回顺序、`Record` 字段与调用方接口不变；`ScopeManager._open`、`kb forget`、去重等路径无需改动。
- 目的：降低大库（数万条以上）打开、重建 BM25 时的单次结果集峰值内存。

### 重启回归用例

- 新增 `tests/test_n42_restart_stability.py`（7 项）：
  - `iter_all` 分页边界（0 / 1 / 500 / 501 / 680）与“必须带 limit”的契约；
  - 680 条库跨 **5 次独立进程重启**的 `count` 与 `iter_all` 一致性。
- 该用例在正常终端下稳定通过；若在受限终端里跑出 HNSW 报错，先按 README 排障排除环境。

## 验证

- 全量：**543 passed / 1 skipped / 91.21s**（Windows，Python 3.10，ChromaDB 1.5.9）。
- 新增用例：7 passed。
- 680 条哑向量建库 + 5 次重启：`count=680`、`iter_all=680`，无索引错误。

## 升级

```bash
pip install -U "kb-memory[ingest]"
```

无需迁移数据；旧库可直接打开。若旧库已经因为外部清理 journal 而损坏，按 README
「重启后报 Error loading hnsw index」一节的步骤先备份、再重建索引。

## 仍未处理

- BM25 单条写入仍会全量重建；`iter_all` 虽然分页，但 `_open()` 仍会把全部记录读入内存，
  10 万条级别的启动内存/耗时仍需专门优化。
- 未新增 `kb repair` 命令：目前没有稳定可测的“损坏库”构造方式，避免发布未经验证的修复工具。
- MCP 业务错误的 `is_error` 标记与依赖版本区间收敛仍未调整。

## 排查记录（给遇到同类报错的人）

1. `healthz` 仍返回 200，`count.txt` 也正常，只有项目库 `search`/`get` 报 HNSW 读取失败。
2. 同一份数据在沙箱里创建、再在普通终端打开，最容易复现；两个方向交替访问也会触发。
3. 记录仍在 `chroma.sqlite3` 的 `embeddings` 表里时，删除 `chroma/<segment-id>/` 索引目录
   可让 Chroma 重建；**操作前必须备份**。
4. 修复代码前先做一致性对照：同一负载、同一终端链路、连续 5 次重启，再判断是不是产品问题。
