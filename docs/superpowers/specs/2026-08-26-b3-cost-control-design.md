# B3 精细化成本管控实施设计（P2）

- 日期：2026-08-26
- 状态：设计书（TASK-0046 产出），待拆实现卡
- 依据：ROADMAP.md B3 节（六子项 + 阶段验收 + 风险）；protocol.md v1.4（轮次硬限制 §4、批量 §9、反馈节点 §11）；B2 反馈设计书（`docs/superpowers/specs/2026-08-26-b2-feedback-design.md`）结构参照
- 难度：★★★（多机制协同，需防摘要丢信息）
- 阶段目标（ROADMAP §5）：同复杂度任务 token 总量比 B2 阶段降 40%+；中断任务可从 kb 恢复上下文

## 0. 设计原则

- **无状态 Agent + 有状态知识库**（总线铁律 3）：上下文不堆在 agent 里，靠 kb 检索召回
- **先文档后代码**：本 spec 定稿后拆实现卡，逐子项走节点门禁
- **YAGNI 分层落地**：六子项分两批，先做收益最大、风险最低的（滚动窗口/增量沉淀/上下文切片），动态配额与模型分级依赖历史数据，后期再开
- **防摘要丢信息**（ROADMAP §6 B3 风险）：核心决策/参数/验收标准强制保留标签，摘要后校验

## 1. 数据模型

### 1.1 轮次计数器（tag=rounds）

每任务一张轮次计数记录，供配额判定与成本统计：

```
ROUNDS TASK-0046 | precheck=1 milestone=0 review=0 total=1
复杂度：simple|medium|complex
配额：precheck=2 milestone=2 total=5（simple）/ 8（complex）
```

- 纯文本 kb 记录，由 board.py/反馈流程在写卡时递增（不引入新服务）
- 复杂度由协调者拆卡时标注（默认 medium），影响动态配额

### 1.2 摘要沉淀记录（tag=summary）

滚动窗口/增量沉淀产出的上下文摘要：

```
SUMMARY TASK-0046 round-2 | <摘要正文≤500字>
保留标签：决策|参数|验收标准|阻塞点（强制不被摘要压缩）
来源轮次：1-2
校验：摘要后回读关键标签是否齐全（缺失则重生成）
```

### 1.3 任务关联（tag=relation）

```
RELATION TASK-0046 -> TASK-0035,TASK-0036
关联数：2（≤5）
```

- 第 6 张关联起，最早关联卡归档摘要（不删原卡，摘要入 summary 后解除关联）

## 2. 流程（文字版）

```
任务启动：
  协调者拆卡 → 标注复杂度（simple/medium/complex）→ 建 rounds 记录（按复杂度给配额）

执行中（每个反馈节点/轮次结束时）：
  1) 上下文切片：当前节点（precheck/milestone/review）只加载本节点上下文，切换节点即清空
  2) 增量沉淀：每 2 轮把关键结论写 summary（含保留标签），agent 上下文清空 → 中断可从 summary 恢复
  3) 滚动窗口：agent 仅保留近 3 轮原文，更早的只保留 summary 摘要（检索召回）
  4) 关联窗口：任务卡关联 ≤5 张，第 6 张起最早关联归档摘要
  5) 配额检查：total 达复杂度配额 → 强制截断转仲裁（同 B2 超限仲裁）

模型分级调度（调用 LLM 前）：
  按任务复杂度选模型：simple→本地低规格(qwen3:1.7b)，medium→本地标准(qwen3:4b)，complex→高规格/云端
  （与 kb /ask 智能路由复用，不新增调度器）
```

## 3. 配额表（动态轮次配额）

| 复杂度 | precheck | milestone | 总上限 | 适用场景 |
|---|---|---|---|---|
| simple | 1 | 1 | **3** | 单文件小改、文档更新、冒烟 |
| medium | 2 | 2 | **5** | 常规功能卡（默认，与 B2 一致） |
| complex | 2 | 3 | **8** | 多模块/设计评审/跨子系统 |

- 配额由协调者拆卡时在卡内"约束"注明（如 `配额 complex`），未注明默认 medium
- 超限处理：强制截断转协调者仲裁（复用 B2 §11 仲裁机制）
- review 复盘不计配额（沉淀性，同 B2）

## 4. 六子项设计

### 4.1 分阶段上下文切片
- 三节点（precheck/milestone/review）各自独立上下文窗口
- 切换节点时 agent 上下文清空，仅从 kb 检索本节点所需（任务卡 + 本节点反馈卡 + 相关 summary）
- 落地：协议层约定（worker/designer prompt 增"按节点加载"纪律），不引入代码组件

### 4.2 滚动窗口
- agent 上下文仅保留近 3 轮原文（当前轮 + 前 2 轮）
- 更早轮次：原文不保留，只保留 summary 摘要；需要时 `search_memory` 召回
- 落地：prompt 纪律 + summary 记录；不做自动截断代码（agent 自律，协调者核验）

### 4.3 动态轮次配额
- 见 §3 配额表；simple 3 / medium 5 / complex 8
- 复杂度判定：协调者拆卡时按"改动文件数/子系统数/是否含设计决策"标注
- 落地：卡约束字段 + rounds 记录 + 超限仲裁（复用 B2）

### 4.4 关联窗口
- 单任务关联卡 ≤5 张（relation 记录）
- 第 6 张起：最早关联卡生成 summary 归档，解除关联（原卡不删，可检索）
- 落地：board.py 增 relation 子命令（实现卡，本期不做）

### 4.5 自动增量沉淀
- 每 2 轮（或节点结束/任务中断时）生成 summary：关键结论 + 保留标签
- **保留标签强制不压缩**：决策、参数、验收标准、阻塞点四类必须原样保留
- 摘要后校验：回读 summary 检查四类标签是否齐全，缺失则重生成（最多 1 次）
- 中断恢复：agent 唤醒时先查 claimed 卡的 summary，从摘要续做（不依赖对话历史）
- 落地：prompt 纪律 + summary 记录格式；摘要生成可复用 kb 本地 LLM（qwen3:4b，强制本地）

### 4.6 模型分级调度
- simple → qwen3:1.7b（本地低规格，快/省显存）
- medium → qwen3:4b（本地标准，默认）
- complex → 高规格/云端（按 KB_LLM_MODE=auto 路由）
- 与 kb `/ask` 智能路由复用同一 LLMClient，不新增调度器；orchestra 侧仅在卡约束注明建议规格
- 显存约束不变：两本地模型禁止同时加载（AGENTS.md），分级是"选一个"不是"同时加载"

## 5. 与 B2 衔接

- B2 反馈节点（§11）是 B3 切片的天然边界：precheck/milestone/review 即切片点
- B2 配额（2/2/5）= B3 medium 档；B3 向下兼容，未标注复杂度的卡按 medium 执行
- B2 超限仲裁机制直接复用，B3 不另建仲裁流程
- B2 反馈卡（tag=feedback）是 summary 保留标签"阻塞点/决策"的重要来源

## 6. 验收标准

**阶段验收**（对照 ROADMAP §5 B3）：
1. token 降量：同复杂度任务 token 总量比 B2 降 40%+（度量：滚动窗口 + 切片后，单任务平均上下文 token 对比）

## 7. YAGNI（明确不做）

- 不做自动复杂度判定（由协调者人工标注，历史数据校准留 B4 自学习）
- 不做 token 计量埋点/计费系统（度量靠抽样对比，不引入监控组件）
- 不做跨任务全局上下文压缩（仅单任务内切片/窗口）
- 不做 B4 的轮次阈值自学习/成本-质量动态平衡（B4 远期）
- 不新增常驻服务/调度器（模型分级复用 kb LLMClient，沉淀靠 kb 记录 + prompt 纪律）
- 六子项分两批落地：第一批 4.1/4.2/4.3/4.5（协议+prompt+记录格式，零代码或少量 board 子命令）；第二批 4.4/4.6（relation 子命令、模型分级联调，依赖第一批稳定运行数据）
