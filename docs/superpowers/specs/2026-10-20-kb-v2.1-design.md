# kb v2.1 设计：项目记忆、分发与资源占用（2026-10-20）

> 本文件是 v2.1 的唯一新增设计依据。基础需求/架构/API 仍见
> `2026-08-23-kb-memory-service-design.md`；两者冲突时以本文件为准。
> 历史 spec/plan 已移入本地 `_archive/`（不随仓库上传）。

## 1. 目标与决策

| 主题 | 决策 |
|---|---|
| 项目记忆 | 全局库 + `kb_data/projects/<project>/` 分项目子库，项目间物理隔离 |
| 分发 | 发布 PyPI `kb-memory`；skill 首次检测到未安装时，经用户确认后安装 |
| 后台 | 登录自启；嵌入模型空闲 10 分钟卸载 |
| 语言 | 按操作系统默认语言书写记忆（`KB_MEMORY_LANG=auto`） |
| 规则 | 用户可在 `~/.kb/rules.md` 与 `kb_data/rules.md` 自定义记忆时机 |
| 文档 | 仓库只保留核心文档 + 本 spec；历史 spec/plan 仅本地归档 |

非目标：不引入外部数据库/常驻中间件；不做云端同步；不做 UI；不自动改写用户已有记忆。

## 2. 项目记忆

### 2.1 目录布局

```
kb_data/
  chroma/                 # 全局记忆与全局知识（project 为空）
  bm25_corpus.json
  projects/
    <project>/
      chroma/
      bm25_corpus.json
      sparse_index.json   # 仅在 KB_SPARSE_ENABLED=1 时生成
```

`<project>` 复用现有 `validate_project` 白名单（字母/数字/中文/下划线/连字符，1~64），
并额外拒绝 Windows 保留名（CON/PRN/AUX/NUL/COM1-9/LPT1-9）。

### 2.2 读写语义

- `project` 为空：只读写全局库（保持旧行为）。
- `project=X`：
  - 写入落到 `projects/X/`；
  - 检索 = X 子库 + 全局库，X 命中加 `KB_PROJECT_BOOST`（默认 0.05），按分数合并去重；
  - 按 ID 读取/更新/删除：先查 X，再查全局；未传 project 时先查全局，再按目录顺序查各项目子库。
- 文档/网页与记忆同规则：带 project 的摄取进入项目子库。
- 同一个安装只使用一个嵌入模型（由全局库 `runtime.json` 决定）；项目子库首次写入沿用该模型。

### 2.3 打开与缓存

- 全局库启动时打开；项目子库首次访问时懒打开。
- `KB_PROJECT_CACHE_SIZE`（默认 4）限制同时打开的子库数量，LRU 淘汰引用。
- 每个子库独立 BM25 / 稀疏索引；写入仍由服务级 `RLock` 串行化。
- 旧数据（v3 全共享时期带 project 元数据的记录）继续留在全局库，不回迁；新写入按新规则落子库。

## 3. 分发与启动

### 3.1 PyPI 包

- 包名 `kb-memory`，版本 `2.1.1`，入口 `kb = kb.cli:app`。
- 核心依赖只保留运行服务与向量检索必需项；可选依赖：
  - `[ingest]`：pypdf / python-docx / markitdown / trafilatura / lxml_html_clean / watchdog
  - `[llm]`：openai
  - `[full]`：以上全部
- 缺失可选依赖时返回可读错误，提示安装对应 extra，不崩溃。
- Linux/Windows 默认 CPU：安装脚本先装 PyTorch CPU 轮子（`download.pytorch.org/whl/cpu`），再装核心包，避免默认 CUDA 轮子带来的数 GB 下载。

### 3.2 skill 引导安装

`skills/kb-memory/bootstrap.py`（仅标准库）：

1. 检测服务是否可达；可达则直接结束。
2. 展示安装计划（目标目录 `~/.kb/venv`、来源 PyPI、预计下载量），必须得到用户确认（`--yes` 跳过交互）。
3. 创建隔离 venv；先装 CPU torch，再 `pip install kb-memory`（可加 `[ingest]`）。
4. 写入 `~/.kb/install.json`：解释器路径、包版本、安装时间、数据目录。
5. 启动 `python -m kb serve --non-interactive`；询问是否启用登录自启。

### 3.3 服务发现与自启

- 发现顺序：`~/.kb/install.json` → `PATH` 中的 `kb` → `importlib.metadata` 中的 `kb-memory`。
- `kb where` 输出服务安装位置、解释器、数据目录与版本。
- `kb autostart enable|disable|status`：
  - Windows：启动目录 `.cmd`（优先 `pythonw.exe`）
  - Linux：`~/.config/systemd/user/kb.service`
  - macOS：`~/Library/LaunchAgents/io.github.fish827.kb.plist`
- `kb serve --non-interactive` 供自启调用，不弹设备选择。

## 4. 资源占用

- `KB_IDLE_UNLOAD_SECONDS`（默认 600，0=关闭）：嵌入模型空闲超时后卸载，
  `state` 回到 `unloaded`，下次检索重新加载；CUDA 下同步释放缓存。
- `kb/api.py` 不在模块导入期加载 watchdog；`serve` 仅在启用 watcher 时导入。
- 空闲后台只有 HTTP 监听线程与一个空闲检查线程，不轮询 LLM。

## 5. 语言与自定义规则

- `KB_MEMORY_LANG=auto|zh|en|...`：auto 按系统 locale；MCP instructions 明确要求
  agent 用该语言书写记忆，专有名词/代码保持原样。
- 规则文件按顺序拼接，总长截断 4000 字符，注入 MCP instructions：
  1. `~/.kb/rules.md`（用户全局）
  2. `kb_data/rules.md`（本安装）
- 规则用于“何时写/不写、写什么、隐私边界”，不替代服务端校验。

## 6. 文档策略

仓库保留：README(_EN)、USER_GUIDE(_EN)、PROJECT(_EN)、ROADMAP(_EN)、AGENTS、
DEV_HANDBOOK、SECURITY(_EN)、AGENT_PROMPT(_EN)、基础设计 + 本 spec。
历史 spec/plan 移至 `_archive/docs/`（git 忽略，不上传）。

## 7. 验收

自动化：

1. 项目 A 写入的记忆在项目 B 检索不可见；全局记忆在 A/B 均可见。
2. 按 ID 读取/更新/删除按上述路由正确，跨项目不可见。
3. LRU 上限生效，超出后最久未用子库被淘汰。
4. 空闲卸载后 `embedder.state=unloaded`，再次检索可恢复。
5. bootstrap 脚本只生成计划不执行；`--yes` 路径在假 pip 下写入 manifest 并启动。
6. 发现顺序与 `kb where` 输出正确。
7. 语言/规则注入内容正确，规则超长截断。
8. 可选依赖缺失时错误信息包含对应 extra。
9. 全量 `pytest tests/` 通过。

人工验证：真实 PyPI 安装、Windows/Linux/macOS 自启、CPU torch 实际下载量、空闲 RSS 对比。
