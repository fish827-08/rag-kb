## 2. P2-2 鉴权（N19-N20）— 待详细设计

**动机**：日志（P2-1）落地后，审计链有了；鉴权补上"谁能操作"。多 agent 并行与局域网访问（手机/其他设备挂 kb MCP）前的安全前置。

方向草案（详细设计另行立项，实施前需 spec 评审）：

- API Key 模式：`.env` 配 `KB_API_KEY`（空 = 不鉴权，保持本地零摩擦默认）
- 中间件校验 `Authorization: Bearer` / `X-API-Key`；MCP 与 REST 同栈覆盖
- board.py 与 kb CLI 读同一 `.env` 自动带 key
- 验收：无 key 请求 401；配 key 后全端点过；本地默认模式行为不变

| 节点 | 内容 | 门禁 |
|---|---|---|
| N19 | 鉴权 spec + 配置与中间件实现 | spec 需人工评审 |
| N20 | CLI/MCP 客户端适配 + 端到端验证 | 标准 |

## 3. P2-3 遗忘机制（N21-N23）— 待详细设计

**动机**：补齐"RAG ≠ 记忆"的核心缺口——当前 kb 只会增不会忘：记忆过时不知、重复入库不去重、矛盾信息并存。

方向草案（三选一或组合，spec 评审时定）：

- **衰减**：按访问时间/频率打分，长期未命中的记忆降权或标记候选删除
- **去重/冲突覆盖**：新记忆入库时检索相似旧记忆（相似度阈值），提示覆盖或合并（如"用户偏好 X"更新为"用户偏好 Y"）
- **维护命令**：`kb forget --stale --days 90` / `kb dedup --dry-run` 人工确认式清理（agent 自动遗忘风险高，先做工具给人/协调者用）

设计约束：删除是危险操作，**默认 dry-run + 显式确认**；每次遗忘记入日志（依赖 P2-1）。

| 节点 | 内容 | 门禁 |
|---|---|---|
| N21 | 遗忘 spec（策略选型）+ 衰减评分 | spec 需人工评审 |
| N22 | 去重/冲突覆盖 | 标准 |
| N23 | 维护命令 + 日志审计闭环 | 标准 |

## 4. P2-4 Web UI / CLI 增强（N24+，最后做）

方向已定：**先 CLI**（终端 + agent 交流优先），Web UI 在 CLI 验证价值后再评估。

CLI 增强候选（按需裁剪）：

- `kb stats`：记忆量/类型分布/检索热度（吃 P2-1 日志数据）
- `kb board`：orchestra 看板的终端 TUI 呈现（status 增强版）
- `kb ask`：终端直接问（不经 agent 的快捷问答入口）

Web UI 仅做最小候选：单页看板（记忆浏览 + 任务板可视化），FastAPI 静态页即可，不引前端框架（与零常驻约束一致）。
