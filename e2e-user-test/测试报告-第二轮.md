## 二、Agensi 上架专项（P0）

对照 Joeri 邮件里的四条硬要求：

| 要求 | 现状 | 判定 |
|---|---|---|
| `SKILL.md` at the root | 在 `skills/kb-memory/SKILL.md`，包根没有；仓库也没有打包脚本产出 zip | ❌ |
| 标准 skill 格式 | 第 1 行是 `***`，第 5 行是一长串 `-----`，不是 `---` 分隔的 YAML front matter | ❌ |
| 配置模板 + 安装说明在 zip 内 | `.mcp.json` 在仓库根、`docs/USER_GUIDE.md` 在 docs 下；skill 自身完全没有安装/启动/配置内容 | ❌ |
| listing 自证价值、不靠跳转 | skill 开头直接假设"kb 是本机常驻服务（默认 8000）"，未安装的用户读完仍不知道下一步做什么 | ❌ |

### 2.1 `SKILL.md` front matter 非标准 [实测]

`skills/kb-memory/SKILL.md` 原始字节：

```
***            ← 第 1 行
（空行）
name: kb-memory
description: kb 本地记忆与知识服务接入规约……
-------------------------------------------------------------------------------  ← 第 5 行
```

标准格式应为：

```yaml
---
name: kb-memory
description: ...
---
```

影响：严格按 Anthropic skill 规范解析的客户端读不到 `name`/`description`，**自动触发失效**。`install_skill_kb_memory.bat` 只校验文件大小、不校验 front matter，所以安装脚本会"报成功"但技能可能不被识别。

### 2.2 内容不自包含 [实测]

当前 SKILL.md 只写了"已挂载 MCP 时怎么用 / 未挂载时 HTTP 兜底"，缺少 Agensi 明确要求的：

- 如何安装 kb（clone、venv、`pip install -r requirements.txt`、`pip install -e .`）
- 如何启动/停止（Windows 一键脚本 vs 命令行）
- MCP 配置模板（`.mcp.json` 内容、端口、鉴权头）
- 安装后如何验证（`healthz` 200、`tools/list` 8 个工具）
- 常见故障（模型下载失败、端口占用、无显卡）

此外 `description` 与正文均为中文；Agensi 是英文市场，至少需要英文 description + 双语步骤。

### 2.3 `server.json` 的 PyPI 路径是死链 [实测]

`server.json` 声明：

```json
"registryType": "pypi",
"identifier": "kb-memory",
"version": "1.0.2",
"runtimeHint": "uvx"
```

实测 `https://pypi.org/pypi/kb-memory/json` → **HTTP 404**。任何通过 MCP Registry / `uvx kb-memory mcp` 接入的用户都会第一步失败。同文件第 43 行还写着默认 `BAAI/bge-m3`，与当前默认 `bge-small-zh-v1.5` 不一致。**要么发布包，要么从 manifest 移除这条路径**，不能留死链。

### 2.4 Agensi 最小可交付包（建议）

```
kb-memory-skill/
├── SKILL.md                 # 包根；标准 --- front matter；英文 description；含完整安装→启动→配置→验证→排障
├── mcp.json.template        # 端口/鉴权占位符
├── scripts/windows/*.bat    # 一键启动/停止（需先修首跑问题）
├── requirements.txt
├── pyproject.toml
└── README.md                # 与 SKILL.md 一致，不依赖外链
```

`SKILL.md` 里应能独立完成：安装 → 启动 → 把 agent 指向 `http://127.0.0.1:8000/mcp/` → 验证 8 个工具 → 失败时怎么办。外部链接只能作为"更多信息"，不能是必经步骤。

## 三、Windows 首跑阻断（P0/P1，均为实测）

### 3.1 独显机器 + 一键脚本首跑必失败 [实测，exit 124]

`start_kb.bat` 用 `pythonw` 隐藏窗口启动；`kb/cli.py:392` 以 `interactive=True` 调用 `resolve_device()`，检测到 CUDA 后会执行 `input_fn("检测到独立显卡，是否启用 GPU 加速？[y/n]")`（`cli.py:164`）。

隐藏终端下 stdin 不可读 → `EOFError` → 进程直接退出。脚本随后轮询 `healthz` 30 秒，超时退出：

```
[INFO] Waiting for health check: http://127.0.0.1:8000/api/v1/healthz
（30 秒后超时，exit 124）
```

**这是新用户双击一键脚本的第一分钟就会撞上的阻断**。建议：

- `resolve_device()` 先判断 `sys.stdin.isatty()`，非交互直接默认 `cpu`；或捕获 `EOFError` 回退 `cpu`
- 或 `start_kb.bat` 显式传 `KB_DEVICE=cpu`（用户后续可改 `.env`）

### 3.2 `.env` 改端口后一键脚本仍探测 8000 [实测，exit 124]

`start_kb.bat` 只读取**环境变量** `KB_API_PORT`，不解析 `.env`：

```bat
set "KB_PORT=8000"
if defined KB_API_PORT set "KB_PORT=%KB_API_PORT%"
```

实测 `.env` 写 `KB_API_PORT=8017`：服务实际监听 8017，脚本仍探测 8000 → 超时。`start_kb_console.bat` 同样固定打印 `http://127.0.0.1:8000`。

建议：脚本解析 `.env` 的 `KB_API_PORT`（或让服务把实际端口写入 `kb.pid` 旁的状态文件，脚本读取）。

### 3.3 快速开始缺 `pip install -e .` [实测 + 文档]

README 快速开始只有 `pip install -r requirements.txt`，但文档多处使用 `kb` 命令（`kb add/search/...`），该命令由 `pip install -e .` 安装。只按快速开始操作的用户会得到 `kb : 未找到命令`。`scripts/README.md:111` 反而写明了需要 `pip install -e .`——两份文档不一致。

### 3.4 README 的 PowerShell 示例不可复制 [实测]

README 在"Windows PowerShell"章节之后，API 示例却写：

```powershell
curl -X POST http://127.0.0.1:8000/api/v1/memories `
  -H "Content-Type: application/json" `
  -d '{"content": "...", "tags": ["偏好"]}'
```

Windows PowerShell 5.1 的 `curl` 是 `Invoke-WebRequest` 别名，不支持 `-X/-H/-d`，实测直接报参数绑定错误。`SKILL.md` 里反而写了正确的 `curl.exe` / UTF-8 字节数组方案——**正确做法在 skill 里，README 里没有**。

另外中文 JSON 在部分 shell 下会触发 `{"detail":"There was an error parsing the body"}` [实测]，示例需要给出 UTF-8 文件的写法（`--data-binary @body.json`）或 Python 片段。

### 3.5 停止脚本的防御不足 [代码]

`stop_kb.bat`：第一段按 `kb.pid` 直接 kill，不校验该 PID 是否仍是 kb；第二段硬编码端口 8000；第三段兜底杀所有命令行含 `kb serve` 的 python 进程。强制结束（`taskkill /F`）后 `kb.pid` 会残留 [实测]。建议：kill 前校验进程命令行/端口，端口从 `.env` 读，残留 pid 视为无效。

## 四、运行时失败体验（P1）

### 4.1 模型加载失败：裸 500 + healthz 报 ok [实测]

把 `KB_EMBED_MODEL` 指向不存在的模型、HF 端点不可达后：

- `POST /api/v1/memories` → `500 Internal Server Error`（纯文本，无错误码、无原因、无修复建议）
- 日志里是一大段 `OSError/HTTPError` 栈
- 同时 `GET /api/v1/healthz` 仍返回 `{"status":"ok","records":0,...}`

用户看到的现象是"服务是好的，但一写就 500"。建议：

- 嵌入模型未就绪时写入返回 `503` + 结构化错误（`EMBED_MODEL_UNAVAILABLE`、模型名、`HF_ENDPOINT` 建议）
- `healthz` 增加 `embedder: "unloaded" | "loading" | "ok" | "error"` 字段
- 首次检索/写入触发的模型下载在日志与 CLI 里有明确进度提示

### 4.2 网页文档按 URL 删除无效 [实测]

- `DELETE /api/v1/documents/https://example.com` → **404**
- URL 编码后再请求 → 404
- 改用 query 参数 → 405
- 本地文件 `DELETE /api/v1/documents/sample.docx` → 200 `{"deleted":1}`

网页入库的 source 就是 URL，用户一旦入错/重复入库，**无法通过 API 清理**。建议：删除接口接受 `?source=` 查询参数或文档 id，而不是把 URL 塞进 path。

### 4.3 同一 URL 重复入库不替换 [实测]

`add_webpage()` / `add_document()` 每次都新建 Record 并 `store.add()`，没有按 `source` 删除旧记录。实测重复入库 `https://example.com` 后，列表与检索里出现重复 chunk。结合 4.2（URL 删不掉），用户没有自助清理路径。建议：同一 source 默认"替换"（先删后加），或提供 `replace=true` 参数。

### 4.4 `kb eval` 被用户治理配置打断 [实测]

`.env` 设置 `KB_DEDUP_ENABLED=true` 后，`kb eval --file tests/eval_zh_50.jsonl` 在写入评测语料阶段抛：

```
DuplicateError: 语义重复（相似度 0.941）
```

完整 traceback、exit 1。`eval_cmd()` 构造 `Settings` 时只覆盖 `data_dir/rerank/sparse`，其余继承用户 `.env`。评测应隔离治理配置（`dedup/decay/freshness` 全关），否则**开启治理的用户无法评测**，结果也不可跨环境比较。

### 4.5 空查询返回全部记录 [实测]

`POST /api/v1/search` 传 `{"query": ""}` → 200，返回所有记录（部分 score=1.0）。这不是崩溃，但语义上应返回 422 或空列表；否则 agent 误传空串会拿到一堆无关记忆，污染上下文。

## 五、Web / 鉴权 / 看板（P2）

1. **`/dashboard/` 实际是 agent-orchestra 看板** [实测]：页面标题"agent-orchestra 看板"，Worker 状态/任务看板/交流窗全空。根页面把它标为"HTML 看板"，新用户会以为这是 kb 的管理界面。建议改名为"协作看板（实验）"，或换成真正的 kb 状态页（记录数、模型、索引、日志入口）。
2. **启用 `KB_API_KEY` 后浏览器打不开根页/看板** [实测]：`/` 与 `/dashboard/` 返回 401（中间件只认 `Authorization`/`X-API-Key` 头），而浏览器地址栏无法带头；`healthz` 匿名可访问。若保留 Web UI，应支持 `?key=` 或对静态页免鉴权；否则在文档里明确"启用鉴权后 Web UI 不可用"。
3. **根页"MCP 端点文档"指向 `/docs`** [实测]：`/docs` 是 REST Swagger（标题 `kb memory service 0.1.0`），不是 MCP 文档，标签与内容不符。
