## 六、仓库自带测试套件实测（389 通过 / 2 失败）

在**干净副本 + 全新安装**的环境下运行仓库自带测试：

```powershell
python -m pytest tests/ -q
```

结果：**2 failed, 389 passed in 54.69s**（日志：`e2e-user-test/pytest.log`）

两个失败都不是"环境偶然"，而是会**稳定复现**的真问题：

### 6.1 `test_设备检测决策` 失败 —— 测试隐含假设"机器有显卡"

文件：`tests/test_n08_api_ext.py:51`

```
>       assert (gs().runtime_file).exists()
E       AssertionError: assert False
```

用例逻辑是：模拟用户交互输入 `y`（同意启用 GPU 加速），然后断言设备选择被持久化到 `runtime.json`。

但源码 [cli.py](./repo/kb/cli.py) 的 `resolve_device()` 是这样写的：

```python
if interactive:
    import torch
    cuda_ok = torch.cuda.is_available()
    if cuda_ok:                      # ← 没有显卡时整段被跳过
        answer = input_fn("检测到独立显卡，是否启用 GPU 加速？[y/n]")
        ...
        settings.runtime_file.write_text(...)   # ← 只有这里会写文件
```

本机 `torch.cuda.is_available() = False`（全新安装的 PyPI torch 是 CPU 版），所以**根本不会走到写文件那一步**，断言必然失败。

- **影响**：任何**没有独立显卡**的用户（正是你新要求里要重点照顾的人群）跑仓库测试，都会看到 1 条失败，进而怀疑项目有问题。
- 类比理解：这条测试实际在断言"你一定有显卡"，与项目"默认 CPU、GPU 可选"的定位自相矛盾。
- 建议：测试改为"无显卡时不再期待 `runtime.json` 被写入"，或显式 monkeypatch `torch.cuda.is_available()` 让两条分支都可测。

### 6.2 `test_旧代码已归档且根目录无残留` 失败 —— 断言了一个不可能存在的目录

文件：`tests/test_n16_regression.py:21`

```
>           assert Path(p).exists(), f"归档缺失: {p}"
E           AssertionError: 归档缺失: _archive/rag_kb
```

该用例要求 `_archive/rag_kb`、`_archive/app`、`_archive/notes` 等路径存在。但 `.gitignore` 明确写了：

```
# 旧学习项目归档（2026-08-23/24）：本地保留历史，解除 git 跟踪不上传远程
_archive/
```

即 **`_archive/` 只存在于作者本机，从未进入 git 仓库**。因此**任何 clone 这个仓库的人，这条测试都 100% 失败**，永远不可能通过。

- **影响**：新用户跑测试必然看到失败；这条测试对"发布出去的项目"没有意义。
- 建议：该用例应标注为"仅作者本机可跑"（如 `pytest.mark.skipif(not Path("_archive").exists())`），或从分发包中排除。

## 七、资源占用实测（与"降低硬件门槛"目标直接相关）

### 7.1 运行期内存

| 指标 | 实测值 |
|---|---|
| 服务进程工作集（**刚启动、未检索**） | **约 7 MB** |
| 服务进程工作集（**检索一次之后**） | **约 2,056 MB** |
| 服务进程私有内存（检索后） | 约 4,246 MB |
| 检索 CPU 开销 | 3 次检索累计消耗 6.58 秒 CPU 时间 |

> **重要更正**：嵌入模型**不是**在启动时加载的——`kb/embedder.py` 是懒加载设计（构造时 `_model = None`，首次 `embed_texts` 才加载），实测构造后 `_model` 仍为 `None`。所以：
> - **启动后不检索**：内存几乎可忽略（实测约 7 MB）；
> - **首次检索/入库之后**：模型加载并常驻，BGE-M3（fp32，约 2.2 GB）使工作集升到约 2 GB，此后一直保持。
>
> 结论：**空闲待命本身很轻，真正的问题是"一旦用过一次，2 GB 就长期占用"**。对 8 GB 内存的机器，这个长期占用是能感知的负担——这正是"换轻量模型"要解决的核心问题。

### 7.2 磁盘占用

| 项 | 实测值 |
|---|---|
| 项目 venv | **1,373 MB** |
| BGE-M3 模型缓存 | **4,353 MB** |
| bge-reranker-v2-m3 缓存（可选精排用） | 2,187 MB |
| **bge-small-zh-v1.5 缓存（轻量替代）** | **92 MB** |
| 运行数据 `kb_data` | 1 MB（空库） |

**关键对比**：轻量嵌入模型 `bge-small-zh-v1.5` 只有 **92 MB**（对 BGE-M3 的 4,353 MB 是 **1/47**），内存占用也会同比例下降。这是降门槛最高杠杆的一个点，而项目**已经支持**通过 `KB_EMBED_MODEL` 切换——只是默认没用它。

### 7.3 CPU 与 GPU

- 全新安装得到的是 **CPU 版 torch**（`2.14.1+cpu`，`cuda.is_available()=False`）→ 默认**完全不占 GPU**，符合你的要求。
- 代价：CPU 上做嵌入推理，单次检索端到端约 105 ms（自带评测集实测），对交互式使用可接受，但批量入库会明显慢。
- 有显卡的用户如果想加速，需要额外按文档换 CUDA 版 torch（README 未展开说明，只在 `AGENTS.md` 里）。

## 八、缺陷与问题清单

### P0 — 阻断性（必须修）

**1. 网页入库在全新安装后 100% 失败**

- 现象：`POST /api/v1/ingest/web` 返回 **500 Internal Server Error**；对应 MCP 工具 `add_webpage` 同样不可用。
- 根因（服务端完整堆栈）：

```
kb/ingest.py:101  →  import trafilatura
trafilatura/core.py:20  →  from .external import ...
trafilatura/external.py:9  →  from justext.core import ...
justext/__init__.py:12  →  raise ImportError(
ImportError: lxml.html.clean module is now a separate project lxml_html_clean.
Install lxml[html-clean] or lxml_html_clean directly.
```

- 说明：新版 `lxml` 把 `lxml.html.clean` 拆成独立包 `lxml_html_clean`，而 `requirements.txt` 只写了 `trafilatura>=1.8`，没有把 `lxml_html_clean`（或 `lxml[html-clean]`）带上。
- **已验证的修复**：`pip install lxml_html_clean` 后，同一请求立即返回 200 `{"source":"https://example.com","chunks":1}`。
- 建议修复位置：`requirements.txt` 增加 `lxml_html_clean>=0.4`（或把依赖改为 `lxml[html-clean]`）。

### P1 — 重要（强烈建议修）

**2. 自带测试在无显卡机器上必然失败（测试隐含假设"有 GPU"）**

- 见第 6.1 节。`tests/test_n08_api_ext.py:51` 断言 `runtime.json` 会被写入，但该写入只在 `torch.cuda.is_available()` 为真时发生。
- **无显卡用户（正是要重点照顾的人群）跑测试必看到 1 条失败**，直接动摇信任。
- 建议：按无显卡分支改写断言，或 monkeypatch `torch.cuda.is_available()`。

**3. `_archive/` 归档测试在 clone 后必然失败（断言了从未入库的目录）**

- 见第 6.2 节。`tests/test_n16_regression.py:21` 要求 `_archive/rag_kb` 等存在，而 `.gitignore` 把 `_archive/` 排除在 git 之外。
- 该用例对任何克隆者都**永远不可能通过**，属"只在作者本机成立"的测试。
- 建议：加 `skipif(not Path("_archive").exists())` 或从分发包排除。

**4. `requirements.txt` 缺少版本上界**

- 无上界导致全新安装拉到 `transformers 5.20.1` / `mcp 2.3.0` / `torch 2.14.1` 等跨大版本组合，本次碰巧能跑，但复现性差、随时间必然漂移。
- 建议：关键包加 `<` 上界（如 `transformers>=4.40,<6`、`torch>=2.2,<3`），或提供 `requirements.lock.txt`。

**5. README 未提供 pip 镜像指引**

- 只写了 `HF_ENDPOINT`（模型下载）镜像，没写 pip 源。
- 实测清华源 403、阿里云源正常，且最大单体 `torch` 有 124 MB —— 国内用户很可能在安装阶段就放弃。
- 建议：README 快速开始处补一句 pip 镜像用法。

### P2 — 体验类（建议修）

**6. `skills/kb-memory/SKILL.md` 的 front matter 不是标准格式**

- 现状：第 1 行是 `***`，第 5 行是一长串 `-----`。
- 标准 skill 格式要求用 `---` 作为 front matter 分隔符（`---` / `name:` / `description:` / `---`）。
- 影响：严格的 skill 解析器可能读不出 `name`/`description`，导致技能无法被自动触发。
- **这条与 Agensi 的沟通直接相关**——对方明确要求"SKILL.md at the root"且"listing 要能自证价值"，front matter 不标准会直接影响能否被识别。

**7. 仓库卫生：两个不该入库的目录被跟踪**

| 路径 | 问题 |
|---|---|
| `.trae-html-share-packages/orchestra/dashboard/index.html.zip` | IDE 产生的分享包，被提交进仓库 |
| `_kb_tmp/close_0056.py` | 临时脚本；且 `.gitignore` 里写的是 `.kb_tmp/`（**下划线 vs 点号不匹配**），所以没被忽略掉 |

- 影响：新用户 clone 后看到与产品无关的杂物，观感差；`.gitignore` 规则也形同虚设。
- 建议：删除这两个跟踪项，并把 `.gitignore` 里的 `.kb_tmp/` 修正为 `_kb_tmp/`（或两者都写）。

**8. 首次启动的 watcher WARNING 干扰判断**

- 默认 `KB_WATCH_DIR=data` 而目录不存在 → 每次启动都打 WARNING。
- 建议：目录不存在时降级为 INFO，或默认值改为空（不启用监听）。

**9. 强制 kill 时 `kb.pid` 残留**

- 实测用 `Stop-Process -Force` 杀掉服务后，`kb.pid` 仍留在目录里（只有正常退出/Ctrl+C 才会走 `finally` 清理）。
- 影响：残留 pid 文件可能让停止脚本误判。属可接受的小瑕疵，但值得在停止脚本里加"pid 已死则忽略"的防御。

**10. `kb eval` 未隔离用户治理配置，开启去重后直接失败**

- 现象：用户 `.env` 设了 `KB_DEDUP_ENABLED=true` 时，`kb eval` 在写入评测语料阶段抛 `DuplicateError: 语义重复（相似度 0.941）` 并退出码 1。
- 根因：评测构造的 `Settings` 只覆盖 `data_dir`/`rerank_enabled`/`sparse_enabled`，其余字段继承用户 `.env`，于是评测语料被用户的去重规则拦截。
- 影响：**开了记忆治理的用户无法跑评测**，评测结果也失去跨环境可比性。
- 建议：评测环境显式关闭 `dedup`/`decay`/`freshness`（评测应只看检索质量，不受治理配置影响）。

### P3 — 说明性（非缺陷）

- `GET /audit` 不带 `client`/`agent` 时返回 422 是**契约设计**（有清晰的中文错误说明），非缺陷。
- `kb dedup` 表格窄终端塌陷属显示问题，非缺陷（见第五节）。
- `POST /ask` 无 LLM 返回 503 是**预期行为**（`KB_LLM_MODE=off` 默认），且附带了中文配置指引，处理得很好。

## 九、针对"安装慢 / 性能 / 内存"的优化建议

### 9.1 安装慢的构成（实测拆解）

全新安装实测耗时 **约 25 分钟**、venv **1,373 MB**。拆开看，瓶颈全部在**下载**而非安装/编译：

| 消耗项 | 体积 | 说明 |
|---|---|---|
| `torch` 轮子 | **124.1 MB** | 最大单体，@300 kB/s 约 7 分钟 |
| `scipy` 轮子 | 41.3 MB | chromadb 系依赖 |
| chromadb / onnxruntime / tokenizers / transformers / numpy 等 | 约 300–400 MB | 累计 |
| BGE-M3 模型 | 约 2.2 GB（首次启动时） | **不在 pip 阶段**，但首次启动会下载 |
| **合计（含模型）** | **约 2.8 GB** | 这是新用户的真实"第一次成本" |

> 关键认知：**pip 只占一半**。真正的另一半（2.2 GB 的 BGE-M3）发生在"第一次启动服务"时。用户感知到的"30 分钟" = pip 25 分钟 + 模型下载。**只优化 pip 不够**。

### 9.2 轻量模型质量实测对比（决定"要不要换默认"的关键证据）

在同一评测集 `tests/eval_zh_50.jsonl`（50 题，hybrid，top_k=5）上实测：

| 指标 | bge-m3（当前默认） | bge-small-zh-v1.5 | 变化 |
|---|---|---|---|
| Recall@1 | 0.740 | **0.760** | ↑ |
| Recall@5 | 0.980 | 0.960 | ↓ 小幅 |
| MRR | 0.841 | **0.847** | ↑ |
| 平均检索延迟 | 105.6 ms | **28.6 ms** | **快 3.7 倍** |
| 模型缓存体积 | 4,353 MB | **92 MB** | **降到 1/47** |

分组看：`keyword` 组 0.706→0.824、`semantic` 组 0.529→0.647 都是**变好**；只有 `distractor` 组 1.000→0.812 变差。

> **诚实的边界**：这是 50 题小样本，±0.02 级别的差异在噪声范围内，不能断言"轻量模型全面更好"。bge-m3 是 1024 维、bge-small-zh 是 512 维，**长文档、跨语言、语义更微妙的内容上 bge-m3 预期仍更强**。所以建议不是"直接替换"，而是**给用户可选档位**。
>
> 但有一点确定：**默认用 bge-m3，让"只是想试试"的新用户付出 4.3 GB 磁盘 + 2 GB 内存的代价，收益与成本严重不匹配。**

### 9.3 优化项清单（含预期收益与改动量）

按"收益/成本比"排序，供后续排期：

| # | 优化项 | 下载量 | 内存 | 磁盘 | 检索质量 | 改动量 |
|---|---|---|---|---|---|---|
| 1 | **默认改轻量嵌入模型**（bge-small-zh，92 MB） | **−2.1 GB** | **−约 1.9 GB** | −4.3 GB | 实测基本持平（见上表） | 小（改默认值+文档） |
| 2 | ~~嵌入模型懒加载~~ **（已实现，无需改）** | — | 启动期约 7 MB | — | 无影响 | 无需改动 |
| 3 | **去 torch，改 ONNX Runtime 推理** | **−124 MB** | −300~500 MB | **−800 MB** | 需实测（int8 量化可能小幅波动） | 中（换推理后端） |
| 4 | **requirements 分层**（lite / full） | lite 省 **200–300 MB** | −300 MB | −800 MB | 无（lite 不含可选重排/稀疏） | 小 |
| 5 | **README 写明安装体积与耗时预期** | 不变 | — | — | — | 极小 |
| 6 | **README 补 pip 镜像指引**（实测阿里云可用） | 感知 **−50%+** | — | — | — | 极小 |
| 7 | **加 `kb doctor` 自检命令** | 不变 | — | — | — | 小 |

组合前 4 项的**目标效果**：pip 下载从约 600 MB 降到约 150–200 MB，首次模型下载从 2.2 GB 降到 92 MB，**总首次成本从约 2.8 GB / 25 分钟降到约 250 MB / 3–5 分钟**；空闲内存从约 2 GB 降到约 100–200 MB。

> **实施状态（2026-10-19，首批已落地）**：第 1、4、5、6 项已实施——
> 默认嵌入模型改为 `BAAI/bge-small-zh-v1.5`、`requirements.txt` 补 `lxml_html_clean` 并补齐版本上界、
> README / `.env.example` 补安装体积预期 + pip 镜像 + GPU 说明（`AGENTS.md`、设计文档 §3.1/§3.2 同步修订）。
> 同时新增**"沿用建库模型"护栏**：换默认值不会让已有数据的库维度不匹配而损坏
> （记录于 `kb_data/runtime.json`，启动日志可见）；配套 9 项测试，全量测试 **400 项通过**。
> 第 2 项经实证**本就已实现**（嵌入模型懒加载，启动期约 7 MB、不加载模型）。
> 第 3 项（去 torch 改 ONNX）与第 7 项（`kb doctor`）待后续推进。

> 第 5 项（写明预期）看起来"没技术含量"，但对差评的抑制最直接——用户能接受"首次需下载约 250 MB"，不能接受"点了一下，25 分钟不知道在干什么"。建议在安装命令旁直接给出体积与耗时提示，并在安装脚本里打印进度。

### 9.4 更细的技术手段（性能/内存）

- **模型档位开关**：加 `KB_PROFILE=light|standard`（或保留 `KB_EMBED_MODEL` 但默认给 light），README 给"质量 vs 资源"对照表，让用户按自己机器选。
- **降低向量维度**：bge-small-zh 为 512 维（bge-m3 为 1024 维），Chroma 存储与检索都更快更省。
- **限制 CPU 线程数与批大小**：嵌入推理默认会吃满多核（实测 3 次检索累计 6.58 s CPU 时间）；给个 `KB_EMBED_THREADS` 上限，避免用户在检索时整机卡顿。
- **ONNX int8 量化**：CPU 推理提速明显、内存进一步下降，是"低配优先"路线里最彻底的一步。
- **长文档降级策略**：入库大文件时用轻量模型批量切分，检索时才用高质量模型（可选，后续再说）。

## 十、其他补充建议（非性能类）

性能与内存相关项见第九节，这里是与缺陷清单对应的其余建议：

1. **GPU 保持默认关闭，并把"无显卡可用"贯彻到测试里**
   现状已符合要求（CPU 版 torch 安装即得，`device=cpu`）。建议在 README 显式写一句："默认 CPU 运行，不占用显卡；有显卡想加速再按第 X 节换 CUDA 版 torch"，让无显卡用户安心。
   同时**修掉第 6.1 节那条"假设有显卡"的测试**——否则无显卡用户跑测试就看到失败，与"对无显卡友好"的目标直接冲突。

2. **加一个 `kb doctor` 自检命令**
   一次性检查：venv 是否就绪、关键依赖是否齐全（正好能提前暴露 `lxml_html_clean` 这类缺失）、模型是否缓存、端口是否可用。这能把"新用户第一个报错"从运行时 500 提前到安装后自检。

3. **修 SKILL.md front matter + 清理仓库杂物**
   front matter 的 `***`/`-----` 改为标准 `---`，并把 SKILL.md 放到仓库根；删除 `.trae-html-share-packages/` 与 `_kb_tmp/` 两个误提交项、修正 `.gitignore` 里的名字不匹配。直接关系到 Agensi 这类 marketplace 的收录与自动触发。

4. **`requirements.txt` 补 `lxml_html_clean` + 加版本上界**
   同时解决 P0（网页入库 500）与依赖漂移问题。

5. **`kb eval` 应隔离用户治理配置**
   测试中发现：若用户 `.env` 里 `KB_DEDUP_ENABLED=true`，`kb eval` 会在写入评测语料时被语义去重拦截而抛 `DuplicateError` 直接失败（实测复现：相似度 0.941 触发拦截）。
   评测用的 `Settings` 只覆盖了 `data_dir`/`rerank`/`sparse`，其余项继承了用户 `.env`。建议评测环境显式关闭 dedup/decay/freshness，保证评测结果可复现、不受用户配置影响。

6. **README 补齐国内网络与预期指引**
   pip 镜像（实测阿里云可用、清华 403）+ 首次安装体积与耗时预期 + HF 镜像 + GPU 说明，一次性说清。

## 十一、关于 Agensi 商业邮件的判断

结合本次实测，对方邮件（Joeri）的核心要求是：

> "every listing is delivered through Agensi as a skill package… **SKILL.md at the root**, plus the config template and setup instructions in the zip… The one condition is that the listing delivers what it promises on its own."

对照项目现状：

| 对方要求 | 现状 | 差距 |
|---|---|---|
| SKILL.md at the root | 有 `skills/kb-memory/SKILL.md`，但不在仓库根目录，且 front matter 非标准 | 需移动/复制到根 + 修分隔符 |
| 自带配置模板与安装说明 | 有 `.mcp.json` 模板、`docs/USER_GUIDE.md`、`docs/AGENT_PROMPT.md` | 基本具备，需打包进 zip |
| listing 能自证价值（不依赖跳转） | skill 内容确实自包含（含 HTTP 兜底、写入规约） | ✅ 方向匹配 |
| 全套开箱即用 | **网页入库 500**、pip 镜像缺失、依赖无上界 | 需先修 P0/P1 再上架 |

**我的建议**：可以上架，但**先修 P0（`lxml_html_clean`）和 SKILL.md front matter**。理由很直接——对方强调"listing delivers what it promises on its own"，而当前版本的用户一旦试到网页入库就会撞 500，这正好踩在对方唯一强调的硬条件上。免费 listing 形态对本地服务是合理选择（不承诺云端托管，与"数据不出本机"的定位一致）。
